# 云端 Qt 契约 v2.0 与 `11` 接口契约 逐条对撞

> 目的：回国后云端联调**必须 100% 满足 v2.0**。本文件列出两侧不一致处，每条给出
> 「v2.0 逐字 — `11` 现状 — 差异性质 — 处置」。
>
> 差异性质三档，**处置方式完全不同，不得混为一谈**：
> - **`[BLOCK]`** 联调会直接失败（key 对不上、字段名不同、闭集不同）
> - **`[GAP]`** `11` 里没有这条契约，网关照 v2.0 实现即可，但 `11` 应补登记
> - **`[MAP]`** 两侧都有、只是命名/形态不同，**网关做映射**（R10.1 已裁「映射由我方网关统一实现」）
>
> 扫描方法与日期见文末。🚫 判定量不写进本文（CLAUDE.md 3.7），逐条结论可用
> `scripts/doccheck/qt_contract_collide.py` 现场复跑。

## A. 最要紧的三条（联调第一天就会撞上）

### A-1 `[BLOCK]` 云端下发的 key 不一致

| | 逐字 |
|---|---|
| **v2.0** | `xbrain/{rid}/cmd/task`（§2 正式 key 全量表首行，Qt → 后端） |
| **`11`** | `xbrain/{rid}/cmd/task/ext`（§2.2，v0.7.8 新增，「★ **云端**（唯一）」→「★ **`p5_gateway`**（唯一）」） |

`11` 同时登记了 `xbrain/{rid}/cmd/task`，但它的发布者是 **`p5_gateway` · HMI · `p4_agent`**，
订阅者是 `p3_task` —— 那是**机内**的任务下发通路。`11` 逐字写着
「⚠️★★★ **`p3_task` 🚫 不得订阅本 key**」（指 `cmd/task/ext`）。

**差异后果**：Qt 发到 `cmd/task`，会被 `p3_task` **直接收到**，绕过网关的信封重建、
`rid` 校验、`task_type` 拆分与错误码映射。这不是"多收一份"，是**外部报文直连任务域**。

**处置**：二选一，**必须在联调前定**：
1. **网关多订一个 key**（推荐）：`p5_gateway` 同时订 `cmd/task` 与 `cmd/task/ext`，
   两者走同一条重建管线；`p3_task` 维持只订 `cmd/task`。
   ⚠️ 但这样 `cmd/task` 上会同时有"外部原始报文"与"机内已重建报文"两种形状，
   `p3_task` 必须能区分 —— 靠 `src` 字段（Qt 固定 `qt_hmi`，机内为 `p5_gateway`）。
2. **要求 Qt 改发 `cmd/task/ext`** —— 但 v2.0 已冻结，改动方是客户，成本高。

### A-2 `[BLOCK]` 外层信封字段完全不同

| | 逐字 |
|---|---|
| **v2.0** | 六字段 `v` / `rid` / `ts` / `seq` / `src` / `data` |
| **`11`** | `cmd/task/ext` 行写「外层七字段 `schema_version`/`msg_id`/`task_id`/`robot_id`/`timestamp`/`task_type`/`payload`，见评审意见书 R1.3」 |

**`11` 记的是客户 v1.0 初稿的字段**，而客户已在 v2.0 全面改用我方建议的信封
（`rid` 取代 `robot_id`、`ts` 取代 `timestamp`、新增 `seq`/`src`、业务字段下沉进 `data`）。
也就是说：**评审提的意见客户采纳了，而 `11` 没有跟着更新**。

**处置**：`[GAP]` 性质 —— `11` §2.2 `cmd/task/ext` 那一行的字段清单**必须改写为 v2.0 六字段**，
否则照 `11` 写网关的人会去解析一组客户不再发送的字段。

### A-3 `[BLOCK]` `ts` 的格式

| | 逐字 |
|---|---|
| **v2.0** | 「**`ts` 明确冻结为 JSON number 表示的 float64 Unix 秒（UTC，可带小数）**」「禁止 ISO 8601 字符串、毫秒整数和本地时区字符串」 |
| **`11`** | 全册只有一处出现 "float64 Unix"；信封 `ts` 的定义散在 §3.0 与 CLK-C3 |

**处置**：`[GAP]` —— `11` 的信封节要补一句逐字冻结，且**明确它只适用于跨主机面**；
机内仍用 `ts` + `mono` 双字段（CLK-C3）。两者不冲突，但不写清楚会让人以为要给 Qt 发 `mono`
（v2.0 §1.1 逐字禁止：「跨主机消息不得携带 `mono`、`boot`」）。

## C. 两侧都有、需网关映射（`[MAP]`）

### C-1 错误码：整数 ↔ 字符串双层

| | 逐字 |
|---|---|
| **v2.0** | `error_code` 是 Qt 稳定整数码（`0/1001..1006/2001..2007/3001`）；「后端原生字符串码放在 `detail.code`」 |
| **`11`** | §8.13.5 标题逐字「错误映射（**网关唯一实现点**）」，左列是 HTTP status |

**这一条两侧是同构的**，且 R10.1 已裁「我方吸收，映射由我方网关统一实现」。
⚠️ 但 `11` §8.13.5 的映射表是 **AI 服务 HTTP → `E_*`**，而这里需要的是 **`E_*` → Qt 整数码**，
是**另一张表**。`11` 目前没有后者。

**处置**：`[GAP]`＋`[MAP]` —— 新建一张 `E_*` → `error_code` 映射表，进 `11` §13 或 §8.13.5 邻节。
★ 该表必须**双向完备**：40 个 `E_*` 每个都要有落点（可多对一），且 13 个整数码每个都要有来源。
🚫 不得出现"未映射的 `E_*` 落到某个兜底整数码"——那会让 Qt 看到一个无法区分的错误。

### C-2 路径 ID 命名

| | 逐字 |
|---|---|
| **v2.0** | 下发用 `recorded_path_id`（`r-[a-z0-9_]{1,40}`）；回报用 `route_id`/`route_rev` |
| **`11`** | 只有 `route_id`/`route_rev` |

**这不是冲突，是 v2.0 有意的区分**：下发的是"计划级权威路径 ID"，回报的是"后端实际加载的"。
v2.0 §3.1 逐字：「后端执行时解析的实际 `route_id/route_rev` 必须在 `state/task` 进度和终态中回报」。

**处置**：`[MAP]` 网关解析 `recorded_path_id` → 查 geo 库 → 得到 `route_id/route_rev` 回报。
⚠️ 两者**可能不同**（例如路径被重录过），这正是 R8.6「版本握手」要覆盖的。

### C-3 `state/link` 的 `state` 字段

| | 逐字 |
|---|---|
| **v2.0** | `state` 三值 `up\|degraded\|down` + `cloud_link`(bool) + `disconnected_s` + `estop_path` |
| **`11`** | §4.6 `LinkState` 用 `level` 整数 0..3（L0/L1/L2/L3）+ `cloud_link` + `disconnected_s` |
| **代码** | `xbrain/p5_gateway/uplink/link_state.py` 产出 `LinkSnapshot(cloud_link, level, disconnected_s, to_next_level_s, reason, ...)` |

**处置**：`[MAP]` 网关做 `level` → `state` 映射。
⚠️ **映射不是一一对应**：`11` 有 L3（返航触发），v2.0 只有三值。L3 该映到 `down` 还是单独告知？
**这一条需要裁决** —— 见 §E。
