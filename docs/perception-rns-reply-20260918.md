## 二、不可逾越的边界（安全 / RT 不变量）

这三核承载的都是"挂了即失安全"的东西，诊断的抖动一律不得触及：

| 核 | 承载 | 为什么绝不借 |
|---|---|---|
| 4 | `xbrain_motion`(P1) 独占，`isolcpus` 隔离 | 20 Hz 唯一速度出口；`10` G-4 要求其周期 P99 不受非实时进程影响；RNS 激光栅格绕障后 P1 单核已占 40-60% |
| 5 | `quadruped` 独占（C++ RT 线程） | 底盘运控 RT 通道 |
| 6 | `zenohd-rt`(7449) + `chassis_relay` + `rtk_driver` + `teleop_input` | 急停链路；`10` §3.2 明令"不能与 Python 共核"（P3 一次 SQLite commit 会把 RT router 转发推迟 5-50 ms）；RT router 在 20 Hz 关键路径上，挂了整个 RT 面同时失明失能 |

★ 加上"离勤 / 静止时测"这一条：即使亲和设置意外泄漏到禁区，也没有正在执行的运动会被扰动。两道防线叠加，诊断对安全零风险。

## 五、诊断方法学的补充要求（不改变贵方方案，仅收严可比性）

贵方方案（同候选/模型/相机/场景、几何+语义+完整媒体、两配置交错各 >= 3 次、每窗 600 s、预热预登记、全留不挑窗、只调批准的资源范围）方法论干净，我方认可。补三条使两组可比、结论可迁移：

1. **两组同一共载**：2 核基线组与 3 核组必须在**相同的共载与 GPU 状态**下跑（见 §一 GPU 行）；否则改善量里混入了共载差异，无法归因到"多一个核"。
2. **报告随附亲和快照**：每窗附 `check_affinity.py --table` 输出与实际借用的核号，使"这一窗到底是几核、借的哪个核"可自证。
3. **同时达标而非分别达标**：贵方也已点明 —— 现有报告未证明 Objects 发布节拍与 Profile 深度节律**同时**达标，部分发布统计还需补齐逐包原始账。诊断结论须以"同一窗内两条支路同时满足 r6 门"为准，🚫 各取最好窗拼接。

## 六、后续路径（正面结果如何变永久）

诊断若显示三核显著改善，**不自动落为部署条件**，须走一次 `10` §3.2 亲和表评审，评审要回答的核心是"永久的第三核从哪来":

- `10` §3.2 本就写着"待 T1-T8 实测后调优"，并列了核 7 过载的解压顺序（① `behavior_proxy` 挪核 6 → ② P2 挪核 6 → ③ 最后才把 `perception` 收回单核）。该顺序解的是核 7，不直接给 `perception` 第三核。
- 因此永久第三核的来源（合并核 1 的云端方向 I/O、或其它重排）是这场评审的开放议题，本轮不预判。
- 评审的输入 = 本次诊断的全部窗数据（含 §五的同载/快照/同时达标口径）。

⇒ 本轮授权到"诊断"为止；"三核是否作为正式部署条件"待结果 + 整机资源评估后另裁。
