## 0. 背景与硬约束

### 0.1 ★★★ 数据来源与降级链（与航向仪表盘同源）

本文全部查询的数据都来自**同一条 RTK 数据流**（架构见 `11` §2.2）：

```
rtk_driver ──(RT 面 zenohd-rt)──> rt/gnss/fix · rt/gnss/heading · rt/clock/status
     │ (rtk_driver 只在 RT 面, 不跨面)
     ▼
p1_motion ★跨面点 ── 订 rt/gnss/* ──> 组装 state/pose (通用面, 含 fix_type/heading_valid/level/source)
     │                             └─ 镜像 rt/clock/status ──> state/clock (通用面)
     ▼
P4 查询 (本文) · HMI 读 state/pose + state/clock (通用面)
```

★★★ **P4 只读通用面的 `state/pose` 与 `state/clock`**，🚫 不直接订 RT 面的 `rt/gnss/*`（跨面白名单只给 `p1_motion`，`11` §1.1.6）。

### 0.2 ★★★ 铁律 VD-3 —— 查询答复由确定性代码生成

母本 `18` §1 **VD-3** 逐字：「查询类答复由确定性代码生成 —— 结构化状态 → 模板 → TTS，**LLM 只做措辞润色，不产生数据**」。

⇒ 本文每条查询的答复走 `configs/query_templates.yaml` 模板库（`16` §6），把 `state/pose` / `state/clock` 的结构化字段填进模板。🚫 **绝不让 LLM 编造 fix 类型 / 精度 / 航向级别**。

### 0.3 表格约定

沿用母本 `18` §0.3：**确认级别** `L0`（查询类直接执行，无复述，母本 §2.4 逐字「查询类 G 全 42 条 = L0」）；**通道** 写「全」＝ `A`＋`C`＋`E`＋`T`＋`H` 五通道。

### 0.4 ★★ 一个必须守住的口径 —— 用最新值，不用首字快照

母本 `18` §0.4 **PS-5** 逐字：「查询类必须用最新 pose —— `G01`「你在哪」答的是**现在**在哪」。⇒ 本文所有查询取 `state/pose` / `state/clock` 的**最新**一帧，🚫 不用 §0.4 的首字快照（那只给「把位置写进对象库」的录制类指令）。

## 2. `G43` `query_rtk_fix` —— RTK 定位状态

**数据源**：`state/pose.fix_type`（闭集 `11` §4.5，逐字 `no_fix` | `single` | `dgps` | `rtk_float` | `rtk_fixed`）＋ `i_fix`（定位质量系数）。

**答复模板（VD-3，确定性）**：`fix_type` → 话术 ＋ 精度档，一一映射（精度档取自 `11` §4.5 定位质量表）：

| `fix_type` | 话术 | 精度（`11` §4.5） |
|---|---|---|
| `rtk_fixed` | 「RTK 固定解，厘米级」 | ≤ 0.05 m |
| `rtk_float` | 「RTK 浮动解，分米级」 | 0.1 ~ 0.5 m |
| `dgps` | 「差分定位，米级」 | 1 ~ 3 m |
| `single` | 「单点定位，精度较低」 | 米级以上 |
| `no_fix` | 「当前没有定位」 | —— |

★ 话术示例（`rtk_fixed`）：「当前 RTK 固定解，定位精度厘米级」。

⚠️★★★ **一个必须守住的口径**：`fix_type` 是**闭集**（`11` §13.6 越界必抛）。🚫 收到闭集外的值**不得**「未知值降级解释」，答复模板必须只覆盖这 5 个值；出现第 6 个值是上游 bug，走故障分支而非编话。

## 3. `G44` `query_satellites` —— 卫星数量

**数据源**：`num_satellites`（GGA 提供）。⚠️★★★ **契约缺口**：该字段现只出现在 `rt/gnss/fix` 的诊断结构内（`11` grep `num_satellites`），**通用面 `state/pose` 未暴露**。⇒ P4（通用面）今天**读不到**它。

**处置（见 §7）**：需在 `11` §4.5 `PoseState` 增 `num_satellites`（并由 `p1_motion` 从 `rt/gnss/fix` 组装进 pose），或本意图暂缓。在字段落地前，`G44` 触发时答「暂不支持查询卫星数量」，🚫 **不得编造星数**（VD-3）。

**答复模板（字段落地后）**：「当前锁定 N 颗卫星」。

---

## 4. `G45` `query_heading_status` —— 航向状态

**数据源**：`state/pose.heading_valid`（`11` §3.3 **H-1**：消费方唯一可用性判据）＋ `heading_level`（1 | 2 | 3）。

★★★ **与 `G08 query_heading`（母本）的分工**：`G08` 答**方向**（朝东 / 朝北，用 `heading_rad`）；`G45` 答**状态**（航向准不准、靠什么、能不能用）。两者不重复。

**答复模板（VD-3）**：先 `heading_valid`，再 `heading_level`：

| `heading_valid` | `heading_level` | 话术 |
|---|---|---|
| `true` | 1 | 「航向有效，双天线固定航向」 |
| `true` | 2 | 「航向有效，航迹推算航向（运动中）」 |
| `false` | 3 | 「当前没有可用航向」 |

⚠️★★★ **只认 `heading_valid`（H-1）**：`11` §3.3 逐字「消费方只认这一个」。🚫 答复逻辑**先看 `heading_valid`** 决定「有效/无效」，`level` 只用来补充说明来源档，🚫 不得用 `level`/`source` 自行反推可用性。

## 5. `G46` `query_heading_source` —— 航向来源

**数据源**：`state/pose.heading_source`（闭集 `heading_source`，`11` §3.3，逐字 `dual_antenna` | `cog` | `none`；共享库导出，见 `common/enums`）。

**答复模板（VD-3）**：

| `heading_source` | 话术 |
|---|---|
| `dual_antenna` | 「航向来自双天线 RTK」 |
| `cog` | 「航向来自行进航迹（COG）」 |
| `none` | 「当前没有航向来源」 |

★ 与 `G45` 常一并回答：「航向有效，来自双天线 RTK」。

## 6. `G47` `query_clock_sync` —— 授时同步状态

**数据源**：`state/clock.sync`（bool）＋ `source`（`11` §3.11，授时源 `rtk` / `ntp` / `rtc` / `none`）。

★★★ **判定权唯一归 `rtk_driver`**（`11` §1.5.3 **CLK-A1**）：`state/clock` 是 `p1_motion` 从 `rt/clock/status` **单向镜像**来的（`11` §2.2.12），🚫 P4 只读不判。

**答复模板（VD-3）**：

| `sync` | 话术 |
|---|---|
| `true` | 「授时已同步，来源 {rtk/ntp/rtc}」 |
| `false` | 「授时未同步，时间可能不准」 |

★★ **与母本 `G24 query_time`（几点了）的关系**：`G24` 播报**时刻**，且 `sync=false` 时必须先声明「时钟未同步」（母本 §9.5 约束）；`G47` 直接答**同步状态本身**，是 `G24` 那条约束的独立查询入口。

⚠️★★★ 授时未同步是 RTK 冷启动期的常态（`11` §1.5.5）。`G47` 的价值正是让现场能主动确认授时是否就绪，🚫 答复不得在 `sync=false` 时报「同步了」。
