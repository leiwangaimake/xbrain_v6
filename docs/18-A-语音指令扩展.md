## 0. 为什么需要这份扩展

`18` **§6.4** 在定义 D 类数值槽位值域时，自己登记了一个洞：

> | ★ **探照灯亮度** | ★★★ **0 – 30**（`BRIGHT_MAX = 30`） | 8529 `MSG_BRIGHT`（`0x02`） | ⚠️ **D 类当前无任何意图携带它**（★ D01 固定下发 30） |

也就是说：**设备支持 31 级亮度，而指令集一级都调不了**。同一节还登记了红蓝灯只有开关、没有图案选择。本文补的就是这两处，并把「设备做不到、但操作员一定会说」的那类说法**显式定为拒绝**，而不是留给模型去猜。

★★★ **本文的三条自我约束**

| # | 约束 |
|---|---|
| **X-1** | ★★ **能靠扩充现有意图的说法解决的，绝不新建意图。** `18` **CMD-02**「同义表达收在意图内」；且 `16` §6.7 的 mission token 最坏组合已是 **891 / 900**，只剩 9 tok 裕度 —— 每新建一个意图都要付 mission 规则 ＋ few-shot 的 token |

### 1.1 ★★ `D17` 的 `level` —— 为什么是闭集档位而不是 `0–100`

| `level` | 映射到 `MSG_BRIGHT` | 典型说法 |
|---|---|---|
| `max` | **30** | 最亮 / 开到最大 / 全功率照明 |
| `high` | **22** | 亮一点点也行 / 调亮些 |
| `mid` | **15** | 亮度一半 / 中等 / 一般亮 |
| `low` | **8** | 暗一点 / 别那么亮 / 灯太刺眼了 |
| `min` | **1** | 最暗 / 调到最低 |
| `up` | **当前 +7**（上限 30） | 亮一点 / 再亮点 / 调亮 |
| `down` | **当前 −7**（下限 1） | 暗一点 / 再暗点 / 调暗 |

★★★ **不用 `0–100` 数值的理由（这是本节的核心，实现者必读）**

`18` **PL-3** 已经警告过：音量的 `0–100` 与亮度的 `0–30`「★ 两者的现场说法都是「调大/调亮一点」，★★ 共用会**静默越界或被截断**，且**事后无告警**」，因此规定两者**绝不可共用同一个校验器**。

★★ **但只把校验器分开还不够。** 若 `D17` 的槽位也定成 `0–100`，那么当**意图被分类错**时——把「音量调到七十」听成 `set_light_bright`——`70` 在两个意图里**都是合法值**，校验器分不分开都拦不住，结果是灯默默变亮而音量没动。

⇒ ★★★ **用一个与音量在类型上不可通约的闭集，让"意图错分"这一类错误在【槽位层】就无法成立**：`set_volume` 的槽位收数字、`set_light_bright` 的槽位收 `max/high/mid/low/min/up/down`，两者的取值空间**不相交**，错分必然触发 `E_SCHEMA` 而不是执行一个似是而非的动作。

★ **附带三个好处**：① 按 **AI-40b**，枚举闭集写进 GBNF 语法**不占 prompt token**（这在 891/900 的预算下是决定性的）；② 说法自然 —— 没人会说「亮度调到 23」；③ 与 `18` **A13 `set_speed_profile`** 的 `profile` 闭集**同构**，实现者不必学新模式。

⚠️ **档位到 `0–30` 的映射是【确定性代码】的职责，不是模型的** —— 模型只输出 `level` 闭集值（CMD-40 同源原则：LLM 不产生数据）。上表的 7 个数值是本文的建议初值，⚠️ 待现场按实际照度整定，整定后回填本表。

### 1.2 ★ `D18` 的 `mode`

| 情形 | 行为 |
|---|---|
| 明确说了序号（「用第三种」） | `mode = 3`，值域 **`1–16`**（`14` §4.3.0 映射表：`MSG_REDBLUE` payload `0x01`–`0x10` ＝ 16 种内置图案；代码侧常量 `REDBLUE_MAX`），越界 `E_SCHEMA` |
| 只说「换一种」「换个样式」 | `mode` 留空 ⇒ ★ **确定性代码取当前模式 +1**（16 回绕到 1），🚫 不由模型猜一个数 |
| 红蓝当前是关闭的 | ★ 本指令**只换图案、不负责开灯** ⇒ 应答提示「警示灯当前是关的」并引导用 `D06` |

⚠️ **`mode = 0` 不在值域内** —— `0` 是「关」，那是 `D07 strobe_off` 的职责。允许 `D18` 传 0 会造出第二条关灯路径，两条路径的状态机迟早分叉。

⚠️★★ **16 种图案的实际差异我方无法内省**（固件细节，`14` GL-4d）。⇒ ★ 若现场只用得上一种图案，本条意图就是纯负担，**应在现场评审后决定是否保留** —— 登记为 **Q-18A-1**。

## 3. ★★★ 显式拒绝规则表（做 prompt 时按此写规则）

> ★★★ **这一节是本文最重要的部分。** 表中三类说法在现场**极其自然**，而设备**物理上做不到**。
> ★★ 若不显式拒绝，模型会挑一个最像的意图去执行 —— 「闪快点」很可能被执行成 `D18` 换图案，**看起来生效了，其实答非所问**，而操作员会以为自己的指令被正确理解了。
> ★ 归宿一律是 **`unsupported`**（`16` §8.0.3 `reason` 闭集内的取值），🚫 不是 `out_of_scope`（那是「超出能力范围的闲聊」，本表是「在能力范围内被问到、但硬件没有」）。

| # | 用户会说 | 判定 | ★ 应答要点（须说清**为什么**，不只是拒绝） | 依据 |
|---|---|---|---|---|
| **R-1** | 把警灯调亮 / 红蓝暗一点 / 警示灯亮度调小 | `unsupported` | 「红蓝警示灯**没有亮度调节**，只能开关和换闪烁图案」 | ★★★ `18` **PL-2**：红蓝亮度**物理上没有这个寄存器**；`0x25` 回读红蓝也只有一个 `0/1` 位 |
| **R-2** | 让警灯闪快点 / 闪慢点 / 调一下爆闪频率 | `unsupported` ＋ ★ **引导改用 `D18`** | 「闪烁快慢**不能单独调**，只能换一种内置图案，要我换一个吗？」 | ★★★ `14` **GL-4d**：`MSG_REDBLUE` 的 payload **只有一个 mode 字节，既无 on/off 时长字段也无频率字段**；★★ **GL-4a** 已裁定主机侧软件定时双闪在本架构下**不可实现**（`POST /lights` 硬超时 300 ms，而双闪脉冲是 70–90 ms 级） |
| **R-3** | 让探照灯闪 / 探照灯爆闪 / 照明灯闪起来 | `unsupported` | 「探照灯**只能常亮或关闭**。它是夜间感知的补光源，闪烁会让相机只在闪光瞬间成像」 | ★★★ `14` **GL-2**：**禁止对探照灯发 `MSG_STROBE[1]`**，合法输出只有 `MSG_LIGHT[0]`（灭）与 `MSG_LIGHT[1]`＋`MSG_BRIGHT[0–30]`（常亮）；★ 后果见 `00` **PER-42** |

★★ **R-3 的历史**：`00` **VOI-43** 记录过这个错误**已经犯过一次** —— 需求原文写「警灯爆闪」，照字面实现就成了 `MSG_STROBE`（探照灯爆闪），「★ 那样**本该常亮补光的探照灯反而在闪**，夜间感知（PER-42）随之失效」。★★★ **2026-08-03 真机复核时在 `services/payload/core/deter.py` 发现同一错误的第二次实例**（驱离模式启动时发的是 `build_strobe(True)`），已修复并补了按值断言的回归测试。⇒ ★ **本表 R-3 的存在意义不是理论洁癖，是这条路已经被走错两次。**

★ **三条拒绝规则的共性写法**：先说**做不到什么**，再说**能做什么**（R-2 给出替代路径）。🚫 只回「不支持」会让操作员反复试不同措辞。
