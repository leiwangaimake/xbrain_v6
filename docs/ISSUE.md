## A. 设备 / 固件问题（厂家侧，不要在代码里绕过）

### A1. `[40]` 录音上行只有 0.25 倍实时速度 — **OPEN，最高优先级**

- **现象**：通过完整 payload-service → WS `/mic` 链路实测，
  **12.7 帧/秒（应为 50 帧/秒）**，即 **0.25× 实时**。
  20 秒挂钟时间只送到 5.08 秒音频；帧间隔 p50 = 76 ms（20 ms 的帧本应 20 ms 一个），
  p90 = 120 ms，max = 316 ms。
  **2026-07-26 复测仍然如此：25 秒挂钟只收到 290 帧 / 5.8 秒音频，0.23× 实时。**
- **根因**：设备每秒只发约 25 个 10 ms Opus 包，而不是 100 个。
  分帧与解码全程零错误，所以**是设备固件特性，不是我们的 bug**。
- **2026-07-26 判定「丢帧」还是「积压」——实测结论：丢帧，没有积压。**
  `[40]` 帧里既没有序号也没有时间戳，光看线上数据无法区分
  「设备录全了但慢慢发」和「设备根本没录/没发」，只能用停止后继续读来判定：
  录 12.10 秒 → 发 `[41]` → 再读 40 秒。
  停止前 282 包 / 2.82 秒音频，**停止后只有 3 包 / 0.03 秒，最后一包在停止后 0.10 秒**，
  合计 2.85 秒 / 12.10 秒 = **0.235×**。
  若设备端缓存着完整音频，停止后应继续吐三十多秒的积压。
  **所以缺掉的 3/4 音频是从未发出，不是延迟送达。**
- **影响**：
  - 人说 1 秒话要 4 秒才送完，VAD 的静音停顿判定被同步拉长 4 倍；
  - 拼接出来的 PCM 时间上被压缩约 4 倍，ASR 拿到的是变速音频；
  - 整个半双工时序无法在真机上标定。
- **2026-07-26 已绕开（功能1 与功能2 都绕开）：AI_runtime 增加本地采集通路。**
  拾音改用**上装到机器狗身上**的测试麦克风，它**替代三合一设备的麦克风**，
  不再走设备 `[40]`；设备只负责放（`[31]` TTS / `[42]` 喊话，下行不受本问题影响）。
  - 实现：`tests/ai_runtime/local_mic.py`，配置 `mic_source=local`（新的默认值）。
    两个音源（`local` / `device`）帧格式完全一致，turn_loop 不知道自己拿的是哪一个，
    厂家修好后改一个配置就切回去。
  - 实测（USB 声卡，真机）：**1.000× 实时**（250 帧 / 5.00 秒音频 / 5.00 秒挂钟），
    开流到第一帧 **44 ms**。对比设备侧 0.235×。
  - **两个功能的拾音都不再经过 `[40]`**，因此 `[40]`/`[41]` 目前无人使用，
    **A1 不再阻塞任何功能**，仅作为厂家侧待修问题保留在案。
  - **注意这不是 A1 的解决方案**，它只是把拾音位置从设备换成了我们自己的麦克风。
    若厂家最终修不好 `[40]`，就用公司的麦克风阵列长期替代这只测试麦克风 ——
    两种情况下设备的麦克风都不再参与，A1 只影响「设备麦克风还有没有用」这一件事。
  - **连带后果（功能2）**：麦克风和设备喇叭现在都在机器狗身上、彼此很近，
    所以功能2 的回声是**真实的声学回路**，不再是网络回灌。
    PTT 闸门必须在 `[42]` 播放期间**照读照丢本地麦克风的帧**
    （与 `turn_loop.py` 功能1 闸门同一套模式：不停读、不关源，理由见该文件模块注释）。
- **已排除的绕行方案**：
  - **先存 wav 再离线交给 ASR —— 无效。** 缓冲能解决「数据来晚了」，
    解决不了「数据从来没发过」（见上面的停止后实测）。存下来的 wav
    就是同一份被抽掉 3/4 的音频，只是换了个容器。
  - **设备端录到文件再用 HTTP 8222 下载 —— 协议里不存在这个命令。**
    8222 只有 `/fetch-files`（列表）、`/upload-file`（我们上传）、`/del-file`（删除），
    写入方向只有「我们上传」；`[12]` 是**播放**文件。
    8519 命令表（14 / 10 / 11 / 42 / 12 / 13 / 15 / 16 / 17 / 31 / 32 / 18 / 19 / 40 / 41 / 89 / 90）
    里没有任何「录音到文件」命令。除非厂家有未公开命令，否则这条路不存在。
  - `[40]` 是**无参数命令**（协议文档 §4 命令表负载栏为「—」），
    没有码率 / 质量 / 采样率开关，我们这侧改不了。
  - **把 asr 和 payload 两个进程合并 —— 无效，已实测。**
    上面那次 0.235× 的测量本身就是「合并到极致」的形态：
    **单进程、直连设备 socket、没有 payload-service、没有 WS、没有 ASR、零 IPC**，
    结果和走完整 payload-service → WS `/mic` → AI_runtime 链路的 0.25× 一模一样
    （厂家风格的独立 probe 也是 0.23×）。三种配置进程数从 1 到 4，速率不变
    → **瓶颈在设备到网线之间，在我们任何一个进程拿到数据之前。**
    量级上也不可能：设备只发 **~3.5 kbit/s**，而本机回环 WS 的带宽是几百 Mbit/s，
    差了五个数量级。
    反向佐证：若真是我们读得太慢，TCP 流控会让设备端积压，
    停止后必然继续吐——而实测停止后只有 0.03 秒。**我们这侧根本没有形成反压。**
- **处置**：已向厂家（疆之载）反馈，**不要写代码去补偿或重采样绕过它**。
  绕过只会把一个固件问题变成一个永久的、错误的时序假设。
  需要向厂家问清的两点：(1) `[40]` 上行是否有未公开的码率/质量参数；
  (2) 设备端能否录到本地文件供 8222 下载。
  除此之外功能1 链路已全部跑通（见 D1 下方的"已验证部分"）。

### A4. 设备没有"TTS 播放完成"事件 — **OPEN（设计约束）**

- **影响**：说话什么时候结束只能**估算**，这是半双工闸门（gate）存在的根本原因。
- **处置**：payload-service 的 `POST /tts` 返回 `est_ms`，
  **真机确认公式为 `字符数 × 180 + 500`**（120 字 → 22100 ms，实测完全吻合）。
  AI_runtime 等待 `est_ms + tts_gate_margin_ms` 后才重新开闸。
  `tts_gate_margin_ms`（默认 700）就是待真机标定的那个数，标定被 A1 阻塞。
- **注意**：`est_ms` 缺失时必须报错，**绝不能默认成 0** ——
  0 会让麦克风立刻开闸，把设备自己的说话声喂回 VAD，正是闸门要防的事。

## B. 已修复的代码缺陷（不要退化）

### B1. LLM 中文回复全部乱码 — **FIXED（2026-07-26）**

- **现象**：真机跑通后，LLM 回复变成 `ä½ å¥½ï¼æ¯...`，
  而设备 TTS 会把这堆乱码照着念出来。
- **根因**：llama-server 的 SSE 流标为 `text/event-stream` 且**不带 charset**。
  `requests` 对任何不声明 charset 的 `text/*` 一律回退到 **ISO-8859-1**，
  于是 `iter_lines(decode_unicode=True)` 用 latin-1 解了 UTF-8 字节。
  （对照：`application/json` 会被映射到 utf-8，所以 REST 客户端没事。）
- **影响**：每一条中文回复都被破坏，且是**可听见的**破坏。
- **处置**：`tests/ai_runtime/llm_client.py` 在状态码检查之后钉死
  `response.encoding = "utf-8"`（SSE 规范本身就是 UTF-8）。
- **回归测试**：`test_a_multibyte_reply_survives_a_stream_with_no_declared_charset`。
  已验证**撤掉修复该测试就失败**（复现出一模一样的乱码），加回来就通过。

### B2. 会话清理时二次 await 已失败的 task，掩盖原始异常 — **FIXED**

- **现象**：`turn_loop._cancel_turn` 在 `finally` 里 await 一个已经抛异常的 task，
  于是在清理阶段抛出同一异常的第二份副本，把真正的原始错误埋掉。
- **处置**：早退守卫改为 `if self._turn is None or self._turn.done()`。

### B3. `0x25` 状态帧的 CRC 只覆盖 payload — **FIXED（已封装）**

这是本链路**最容易搞错的一件事**：
- 状态帧 `0x25`：CRC 只覆盖 **payload**；
- 控制帧：CRC 覆盖 **len + MSG_ID + payload**。

已在 `services/payload/protocol/lights_8529.py` 两侧封装
（`status_crc_ok()` 用 payload-only 规则，`build_control_frame()` 用 len+id+payload 规则），
framer 本身保持纯结构、不做 CRC 校验。**不要让调用方自己选范围。**

### B4. 8529 socket 关闭时有未读数据导致 RST，丢掉最后一帧 — **FIXED**

- **现象**：探照灯关不掉，一直亮着。
- **根因**：8529 会以 500 ms 节奏持续推 `0x25` 状态帧；
  带着未读接收数据 `close()` 会让 Linux 直接发 TCP RST，把刚发出的关灯帧丢掉。
- **处置**：`device_link` 采用 flush-close ——
  先排空未读接收数据、等待 `close_flush_ms` 再 `close()`。
- **验证**：关灯后务必用状态回读确认（payload[3] 的 b7 = 0）。

### B5. 探照灯亮度在关灯后仍保留在状态字节里 — **FIXED（认知陷阱）**

只有 b7（开关位）会被清掉，亮度位不清。
所以 **探照灯字节 = 0x1E 表示"关着、记忆亮度 30"，不是"开着"**。
判断亮/灭只看 b7。

### B6. 45 条热词里有 15 条不在模型 symbol table 里 — **FIXED（启动即告警）**

- **现象**：`趴下`、`开始巡逻`、`返航`、`红蓝爆闪`、`开始驱离` 等 15 条
  含有模型词表里没有的字，无法参与热词加权。
- **处置**：加载时对照模型 symbol table 校验，
  启动日志明确列出哪些词、缺哪个字，只把有效的 30 条送进去。
  **不要静默丢弃** —— 否则热词"配了但不生效"完全无法察觉。

### B7. VAD 从能量门限换成 silero — **FIXED（2026-07-26），不要退回能量**

- **原缺陷**：能量 VAD 只会测响度，测不了"是不是人声"。
  任何能让安静说话的人被听见的阈值，同样会被关门声、拖椅子、风机启动越过。
- **为什么后果比"多切一段"严重**：zipformer 是纯中文模型，
  没有"这不是语音"这个输出（见 C5），拿到一段风机声它会回一个像样的中文字，
  然后 turn_loop 就去回答一个没人问过的问题。
- **实测对照**（Orin，16 kHz，阈值 40）：

  | 信号 | 平均绝对幅度 | 能量判定 | silero 判定 |
  |---|---|---|---|
  | 220/440/1000 Hz 连续正弦 | 6178–6258 | **语音** | 非语音 |
  | 白噪声 0.2 | 5197 | **语音** | 非语音 |
  | 方波 220 Hz | 9830 | **语音** | 非语音 |
  | 恒定直流 900 | 900 | **语音** | 非语音 |
  | 真人录音 `test_wavs/0.wav` | — | 语音 | 语音（5.60 s 里切出 5.16 s） |
  | 真实房间底噪（本机麦克风实采 5.8 s） | 0.9–3.4 | 非语音 | 非语音 |

- **代价**：Orin CPU 上每个 32 ms 窗口 0.25 ms，RTF 0.008，可以忽略。
- **结构**：**只把"这一帧是不是语音"交给模型，分段状态机仍然是自己写的**
  （迟滞、preroll、最短/最长时长都在 `tests/ai_runtime/vad.py` 里）。
  没有用 sherpa-onnx 自带的 `VoiceActivityDetector` —— 那个会替你决定一轮对话何时开始结束。
- **两个容易踩的坑**：
  1. **窗口对不齐**：麦克风帧 320 采样（20 ms），silero 窗口 512 采样（32 ms），
     不整除。每 8 帧里有 3 帧凑不满一个新窗口，只能沿用上一次判定。
     最多滞后 20 ms，对 120 ms 起始沿 / 500 ms 结束沿没有影响。
     **不要为了对齐去重采样音频** —— 那是为了记账去改模型看到的东西。
  2. **silero 有记忆**：它是循环网络，每个窗口的判定依赖前面的窗口。
     Speak 阶段被门控丢掉的帧从来没进过模型，所以 `reset()` 必须一路调到模型，
     否则下一轮 Listen 的头几个窗口会拿"麦克风根本没送过的音频"当上下文。
- **`vad_backend=energy` 保留，但只用于测试**：

### B8. SIGTERM 不展开，功能2 停掉后 payload 卡在 `func2` — **FIXED（2026-07-26）**

- **现象**：`nohup python3 -m tests.ai_runtime.app --function 2` 起来后
  `kill -TERM`，进程直接消失，日志里**一条收尾都没有**，
  `/status` 仍然是 `{"mode":"func2"}`。下一个想用设备的进程就被 R3 挡住。
- **原因**：还原模式的代码在 `IntercomServer.run()` 的 `finally` 里，
  而 SIGTERM 的默认处理是**直接终止进程**，什么都不展开，`finally` 根本不跑。
- **为什么偏偏功能2 踩得到**：功能2 的 `serve_forever()` 没有自然终点，
  **信号是唯一的停止方式**；而 nohup 起的进程又只能被信号停、不能 Ctrl-C。
  也就是说这条泄漏路径不是边角情况，而是**每一次正常停止**。
  功能1 之前没暴露它，纯粹因为一直是在前台 Ctrl-C 停的。
- **修复**：`tests/ai_runtime/app.py` 把 SIGTERM 映射成 `KeyboardInterrupt`，
  和 Ctrl-C 共用同一条收尾路径 —— `asyncio.run` 会取消任务、
  让各级 `finally` 跑完（包括 `await` 出去还模式）。
  不另写一套信号驱动的关停逻辑，就是为了让唯一的那条路径天天被 Ctrl-C 走到。
- **实测对照**：修复前 `kill -TERM` 之后 `mode=func2`；
  修复后日志出现
  `server closing → server closed → payload mode func2 -> idle → interrupted by operator`，
  `/status` 回到 `idle`。
- **不要退化成**："启动时先强制切 idle"。那是拿补偿掩盖泄漏，
  而且会踩 R3 —— 一个没拿到模式的进程不该去还别人的模式。

## C. 测试方法学陷阱（最容易造出"假绿"的一类）

> 本节里 **C3 最值得记住**：本轮两次拿到"绿色"，两次都毫无意义。

### C1. 假服务器的 Content-Type 掩盖了真实的编码 bug — **TRAP**

单元测试里的 `http.server` 统一回 `application/json`，
而 `requests` 对 `application/json` 映射到 **utf-8**、
对不带 charset 的 `text/*` 回退 **ISO-8859-1**。
于是 B1 那个 bug 在单测里**永远测不出来**，而且是"因为错误的原因而通过"。

**规避**：假服务器必须复刻被测服务真实的 Content-Type。
现在 `test_clients.py` 的路由支持三元组 `(status, payload, content_type)`，
SSE 路由用 `_sse_route()` 发裸 `text/event-stream`。

### C2. `json.dumps` 默认 `ensure_ascii=True`，让编码 bug 无法被检测 — **TRAP**

默认会把中文输出成 `\uXXXX` 转义，线上字节**全是 ASCII**，
任何字符集错误都伤不到它。llama-server 发的是裸 UTF-8。

**规避**：构造被测的非 ASCII 载荷时必须 `ensure_ascii=False`。

### C3. 必须验证"回归测试真的能抓到这个 bug" — **TRAP**

写完回归测试后，**把修复撤掉跑一遍，必须失败**；不失败说明测试是空的。

本轮踩了两次：
1. 第一次撤销用 `sed`，但在**单引号包裹的 ssh 命令里反斜杠是字面量**，
   替换根本没生效，得到"测试通过"的假阳性 —— 差点就据此认为测试有效。
2. 修好第一次后测试**仍然**通过，才发现真正原因是 C2（载荷全是 ASCII 转义）。

两次都是"绿色"，但都毫无意义。**绿色不等于验证过。**

### C4. 异步测试里用 `asyncio.sleep(0)` 造假数据流会跑赢被测代码 — **TRAP**

`_FakeMic` 原本每帧 `await asyncio.sleep(0)`，
几毫秒内就消费掉几千帧填充数据，比回合任务的三次 `asyncio.to_thread` 往返还快，
于是流在回合中途就结束、任务被取消，测试报 `assert [] == ['好的']`。

**规避**：填充帧必须走**真实时间**（`await asyncio.sleep(0.001)`），
并给一个帧数上限防止测试跑飞。

### C5. ASR 对纯数字静音会幻觉出字符 — **TRAP（已知行为，未修）**

- **现象**：喂 1 秒纯静音（全 0 PCM），ASR 返回 `'卷'` 而不是空串。
- **影响**：`turn_loop` 里 `if not heard.strip()` 这道空转写保护
  **挡不住 VAD 误触发** —— 关门声、咳嗽触发 VAD 后，ASR 会给出某个字，机器人就会去回答它。
- **现状（2026-07-26 更新）**：换成 silero VAD 之后（B7），
  "超过阈值的非语音"这条路已经基本堵死 —— 实测正弦、白噪声、方波、直流
  这些幅度 900–9830 的信号 silero 全部判为非语音。
  纯静音本来就走不到 ASR（底噪 1–3，远低于任何阈值）。
- **仍未修的部分**：silero 是概率模型，不是保证。
  一段被误判成语音的非语音仍然会拿到一个中文字，
  `if not heard.strip()` 这道保护依然挡不住它。
- **待办**：兜底的修法是最短转写长度或 ASR 置信度门限，
  属于策略问题，应和 D1 一起在真机标定时决定，不要现在拍脑袋加。
  **注意顺序**：先有 silero 把大部分垃圾挡在外面，再谈兜底阈值；
  反过来（用长度阈值去补一个测不了人声的 VAD）会把正常的短命令一起挡掉。

## E. 环境 / 工程陷阱

### E1. 仓库打包方式：没有 `__init__.py`

全仓库没有 `__init__.py`、没有 `conftest.py`、没有 `pytest.ini`，用的是隐式命名空间包。因此：

- 测试文件**必须用绝对导入**（`from tests.ai_runtime.config import ...`），
  用相对导入（`from .config import ...`）会让 pytest 收集直接失败；
- 必须在 `/opt/xbrain_v6` 目录下跑 `python3 -m pytest`（靠 cwd 进 `sys.path`）；
- 应用入口必须用 `-m` 形式：`python3 -m tests.ai_runtime.app`，直接跑文件路径会破坏包内相对导入；
- 放在 `/tmp` 的临时脚本要跑仓库代码，必须 `PYTHONPATH=/opt/xbrain_v6`
  （直接 `python3 /tmp/x.py` 会把 `/tmp` 而不是仓库放进 `sys.path`）。

### E2. `cd X && nohup A & nohup B &` 会让 B 丢掉工作目录 — **TRAP**

`&` 把整个 `cd X && nohup A` 绑成**一个**后台作业，
第二条 `nohup B` 仍在原目录（家目录）执行。
本轮 asr-service 就是这样启动失败的：`ModuleNotFoundError: No module named 'services'`。

**规避**：每条后台命令各自带上 `cd`，或用 `;` 分隔而不是让 `&&` 跨过 `&`。

### E3. 版本约束

- Orin `/usr/bin/python3` = **3.10.12**，`requests` 固定在 **2.25.1**。
- **py3.10 的 f-string 不能嵌套同种引号**。
- 开发机 `python3` 是 miniconda **3.13**，**没有 fastapi/uvicorn** →
  任何 app import / HTTP 冒烟测试都必须在 Orin 上跑。

### E4. 测试必须在设备端跑

开发机 `/opt/xbrain_v6` 是 Orin 的 sshfs 挂载：**本地改代码，到 Orin 上跑测试**。
只有设备端运行才代表机器人的真实反应。

### E5. 单元测试要排除硬件验收脚本

`tests/payload/accept_m3_device.py` 会驱动 192.168.144.38 的真实硬件，
跑单元测试时必须 `--ignore=tests/payload/accept_m3_device.py`。

### E6. 服务启停

启动顺序无依赖，但 payload-service 独占设备 socket：

```bash
cd /opt/xbrain_v6
python3 -m services.payload.app      # 127.0.0.1:18080，独占 8519/8529
python3 -m services.asr.app          # 127.0.0.1:18081，加载模型约 1.3 s
services/llm/llm_server.sh           # 0.0.0.0:8080  <- 注意不是回环
```

**监听地址不一致，别记混**：payload-service 和 asr-service 把绑定地址**硬钉在回环**
（代码里是模块常量，不从 config 取，防止把"本服务的绑定地址"和"设备地址"搞混）；
而 `llm_server.sh` 默认 `LLM_HOST=0.0.0.0`，**在局域网上可达**（设计如此，方便远端调用）。
若不需要off-box 调用，起服务时设 `LLM_HOST=127.0.0.1` 收紧。

停止用 `SIGTERM`（不要 `SIGKILL`）——
payload-service 需要走完 flush-close 才能干净释放设备并把模式重置回 idle（见 B4）。

### E7. 设备网段的静态 IP 必须持久化，且必须禁掉默认路由 — **FIXED（2026-07-26）**

- **现象**：ORIN 重启后 ping 不通 192.168.144.38，链路是好的（`carrier=1`）但网卡没有地址。
- **根因**：之前的地址是用 `ip addr add` 临时加的，**内核态、不落盘、重启即失**。
  这台机器没有 netplan 配置，NetworkManager 里那条有线连接是 DHCP 且处于 disconnected，
  而设备网段没有 DHCP 服务器，所以永远拿不到地址。
- **处置**：把 `enP8p1s0` 配成静态并交给 NetworkManager 持久化：

  ```
  ipv4.method            manual
  ipv4.addresses         192.168.144.100/24
  ipv4.never-default     yes        # 关键，见下
  connection.autoconnect yes
  ```

  落盘在 `/etc/NetworkManager/system-connections/Wired connection 2.nmconnection`。
- **`never-default` 为什么是关键的一行**：这条链路**不配网关**，而且要显式声明
  它不能当默认路由。否则设备网段有可能把默认路由从 wifi 抢走 ——
  而 wifi 正是 ssh 和 `/opt/xbrain_v6` 那个 sshfs 挂载走的路（见 E4）。
  抢走的后果不是"网络变慢"，是**开发机与 ORIN 的连接当场断掉**。
  改完必须回读确认默认路由仍在 `wlP1p1s0` 上。
- **网卡名是稳定的，可以写死**：`enP8p1s0` 是 systemd 按 PCIe 拓扑
  （`platform-140a0000.pcie-pci-0008:01:00.0`，domain 0008 / bus 01 / slot 00）推出来的名字，
  不是发现顺序决定的，重启不变。**只要不换插槽就不会变。**
- **验证**：`ping -c 3 192.168.144.38` → 0% 丢包，0.48 ms。

### E8. USB 声卡的麦克风输入是悬空的（没接咪头）— **TRAP，硬件问题**

- **现象**：本地采集通路一切正常，但录到的音频是"平的"：
  静音 mean|x| 62–67，**敲打麦克风时最大值也上不了 98**。
  正常咪头被敲一下会打到接近 32767。
- **误判风险**：这种失败**看起来像软件正常**。采集是 1.000× 实时、开流 44 ms、
  帧数一帧不差、退出干净 —— 每一项软件指标都是绿的，**只有内容是废的**。
  如果只看"跑通了没有"，会一路把它当成能用的麦克风，直到标定出一个纯噪声的阈值。
- **判定方法（不要靠猜，要测）**：
  1. 先排除静音：`amixer` 读到 `Capture 408 [82%] [25.50dB] [on]`，没被静音；
  2. 敲击测试：20 秒里敲麦克风，波形毫无反应 → 不是电平低，是没有信号；
  3. **FFT 定性**：**60.0 Hz 归一化幅度 1.000，谐波在 120 / 180 / 240 Hz**，
     0–100 Hz 频段能量 1.526 而 1000–3000 Hz 只有 0.124。
     这是**高阻输入悬空当天线收市电工频**的典型特征，不是任何声学信号。
- **结论**：ADC 在工作，咪头没接上。属于硬件，软件侧无事可做。
- **影响**：阻塞 vad_threshold 说话电平标定（见 D 节功能1 条目）、
  `tts_gate_margin_ms` 时序标定、功能1 全闭环、以及 A6 用麦克风做音量客观回读。
- **处置**：已交用户接实体咪头。**软件通路本身已证明是好的** ——
  它正忠实地以 1.000× 实时投递 60 Hz 交流声。
- **咪头接上后的执行顺序**（两个工具都已写好、都已单测，等的只是硬件）：
  1. `python3 -m scripts.ai_runtime.measure_mic_level` —— 定 `AI_VAD_THRESHOLD`，不发声；
  2. `python3 -m scripts.ai_runtime.measure_tts_timing` —— 定 `AI_TTS_GATE_MARGIN_MS`，
     **会发声、要有人在场**；
  3. 再跑功能1 全闭环。
  顺序不能反：第 2 步靠麦克风听喇叭，第 1 步先证明这只麦克风真的听得见东西。
