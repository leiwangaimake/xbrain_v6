### 本轮最重要的一条结论

不是任何单个缺陷，而是一个**反复出现的形状**：

> **模块按契约实现了、有测试、测试全绿，而生产代码一次都没调用它。**

本轮抓到三次（详见第四节）。其中 `ext/estop` 更进一步：它连报文形状都是错的，
而**测试夹具照着同一个错误假设写**，两边"对上了"——接线那天才发现每一条合规急停都会被拒。

⇒ 已加 `tests/repo/test_no_new_unwired_modules.py` 锁基线。
全库 373 个模块中 **159 个没有任何生产 import（43%）**。

## 四、反复出现的失效形状

下一轮**优先照着这几条去找**，比逐条读代码有效。

### 形状一：建了、测了、没接线

| 模块 | 设计职责 | 实际 | 处置 |
|---|---|---|---|
| `Dispatcher.assert_complete` | 缺执行器就拒绝启动 | 零实例化 | 接上（09-04） |
| `mode/b_mode_forward` | B 模式 gen 守卫 | 零调用，且按不存在的 `chunk_gen` 判 | 按 §9.3 删除 |
| `ext/estop` | 急停回执七字段 + 100ms 判据 | 零调用 **且形状全错** | 接上并修正 |

三者都有测试、测试都绿 —— **测试证明了模块能用，没证明系统用了它**。

### 形状二：夹具与被测代码共享同一个错误假设

- `ext/estop` 读 `data.action`，夹具也造 `data.action` ⇒ 两边"对上了"，
  真形状是 `data.payload.action`，接线才发现每条合规急停都会被拒
- `test_task_state` 的建表 DDL 是**手抄副本**（注释还标着 "the real SQL"），
  已与真 schema 漂移十几列 ⇒ 改成 `import DDL_TASKS`，必填列由 `PRAGMA table_info` 现算
- `test_audio_state_build` 的 `_view` 桩自己做了 `if speaking else "none"`，
  使被测代码里同一句判断一次都没被测到（变异体存活才发现）

### 形状三：兜底值退化成常量

- `result_code` 的 `or 2001`：p3 **从不写** `result_code` ⇒ 每条非 done 终态都报
  "机器人未就绪/授时未同步"，与真实原因无关
- `total_count` 的 `or 0`：p3 送空 progress ⇒ 甲方界面显示 `0/0`
- 共同点：**主来源不存在时，"通用兜底"就是唯一取值**，而它断言了一个具体的假原因

### 形状四：被另一个故障掩盖

- B 模式不关麦克风门 —— 麦克风本来就没出帧（`devices.mic=fail`），所以没暴露
- p2 急停事件 `ts: 0.0` —— record 层与云端信封层各自兜底了，只有 HMI 事件环直读

### 形状五：两个字段表达同一件事

- ack 与 `state/mode` 曾共用一个 `stream_id`：ack 退出时要回显原值，
  状态面退出后必须为 null ⇒ 实测退出后云端仍带着旧 ID。
  改为**状态面由结果态推导**，不抄回调返回值。
