## 1. 进程形态

### 1.1 ★★★ 单进程 · 五执行体 · 两条 Zenoh 会话

```text
  perception (C++17, 单进程)
  ├─ ① 采集线程        Orbbec SDK 回调: 深度帧 + 彩色帧 --> 各自 latest-wins 槽
  ├─ ② 快线 (几何)     每个深度帧: ProfileMsg 生产管线 (S3) --> RT put
  ├─ ③ 慢线 (推理)     检测 + 分割 + 跟踪 (基底既有) --> ObjectsMsg --> RT put
  │                     ├─ 分割 mask + t_seg --> latest-wins 槽 (快线消费, S3.3)
  │                     └─ 语义 footprint + t_obj --> latest-wins 槽 (快线消费, S3.4A)
  ├─ ④ status 线程     1 Hz StatusMsg --> RT put; 事件边沿 --> GEN put
  └─ ⑤ ROS executor    TF 监听 (odom<-base_link, quadruped 到位后) + capture_cmd 订阅
  会话: RT session --> tcp/127.0.0.1:7449 (rt/perception/*)
        GEN session --> tcp/127.0.0.1:7447 (event/{sev}/perception; 停车场区不发)
```

| ★★★ **P19-1** | ★★★ **快线 🚫 不等慢线**（`11` TIME-2）。快线对慢线的唯一依赖是**读一个 latest-wins 槽**（最新 mask ＋ `t_seg`），槽空就按无 T 证据发（§3.3） |

## 2. 时序架构（`11` TIME-1 ~ TIME-3 的实现）

### 2.1 ★ 为什么拆快慢线

★ 规范与理由的定义处是 `11` §3.1B.0（吞吐 ≠ 延迟 · `d_block` 不得等推理），🚫 本节不复述。本节只给**实现侧预算**。

### 2.2 ★★★ 快线预算（两道门 · v1.3 命名：**G-P1** 处理时间 · **G-P2** 发布时年龄 ≤ 60 ms）

| 段 | 预算 | 依据 |
|---|---|---|
| 曝光中点 → 帧完成 | ~17 ms | 30 fps 半周期（全局快门，无 rolling 校正） |
| GigE 传输 640×400×16bit | ~4 ms | ≈ 123 Mbps 瞬时 / 千兆链路 |
| SDK 解包 → 槽 | ≤ 2 ms | 零拷贝或单次 memcpy |
| ★ 逐像素遍历（§3.2） | ≤ 8 ms | 256 k px × ~30 flops，单核 NEON（§3.6） |
| 逐 bin 后处理 ＋ 序列化 | ≤ 3 ms | 181×24 cell ＋ ~10 KB JSON |
| RT put | ≤ 1 ms | 环回，非阻塞（§3.5） |
| **合计** | **≤ 35 ms** | ★ 对 T-50（300 ms）留 ~8 倍裕量 |

★★ **预算是 CI 断言不是愿望**（A19-PERF-1，§14）。★ **v1.3 把两道门分开命名**（感知方 09-11 Q2 追问「处理 P99 硬门的准确数值与起止点」）：**G-P1 处理时间** = SDK 深度帧回调返回 → `put` 返回，**P99 ≤ 14 ms**（解包 2 ＋ 遍历 8 ＋ 后处理/序列化 3 ＋ put 1；A19-PERF-1 的锚；开发机现在可测、生产机共载复测；★ v1.8（2026-10-26 感知方同步）：负责人 2026-10-26 起 14 ms **不再作过线条件**，见本节 v1.8 注记）；**G-P2 发布时年龄** = `t_publish − t_capture`，**P99 ≤ 60 ms**（独立门，含曝光半周期与传输；⚠️ 只有 PD-11 闭合后才能签，此前按 `t_capture_estimated` 报数不签）。🚫 两者相加或混用。

> ★ **原文是什么**：本段伪代码的负障碍分支原写 `h_out[i] = neg_flag[i] ? (实测到坑内点 ? neg_h[i] : null)`，而 `neg_h[i]` 由 §3.2 遍历中 `neg_h[i] = min(neg_h[i], p.h)` 对**该 bin 的全部坑内点**取最小 —— **不问这些点离坑沿多远**。

### 13.1 MED-2 · NVENC 推流

v0.1 裁定**原样沿用**：环回 RTSP **18084**（★ v1.8（2026-10-26 感知方同步）：~~18083~~ **被替代的表述**，生效区间 v0.1 – 2026-10-26 —— 平台 `p5_gateway` 的 HMI 网页口 `hmi.web.port` 也是 18083（`configs/p5_gateway.yaml` `hmi.bind` 含 `127.0.0.1:18083`，U7「AI 服务端口顺延」），两进程同绑 `127.0.0.1:18083`、谁先起谁占；感知让出，感知方用户 2026-10-26 定改 18084，.26 上该口空闲已查）（`127.0.0.1` only，NET-C9）；`rgbd_pub_port` 属甲方 `U-15`（PD-2），未配置 ⇒ 不推流 ＋ 一条 `warn`（`med2_not_configured`），其余功能照常；H.264 NVENC `zerolatency` B 帧 0，1280×720@15，2000 kbps CBR，GOP 30（码率/分辨率待现场实测，PD-8）。★ 与 §6 路线 3（GPU 分担模型）有资源交叠，选该路线时 NVENC 占用须一并实测。★★ **v1.3 澄清（感知方 Q3 追问）**：MED-2 是**独立的预览 / 上行编码支路**（HMI / 云端拉流），🚫 不是对分析管线帧输出的旧描述；分析 · 检测 · mask 走 **1280×800 主输出**（2026-09-11 负责人裁定，🚫 再生成 1080p 规范化流 —— XBRAIN 侧无任何 1080p 消费者）；联合验收时**两路同时运行**计入共载。若 PD-8 实测后 RTSP 改 800p，仍是两路。

★ **v1.8（2026-10-26 感知方同步）· 现行实现与新需求**

> ① **现行实现**（感知方 `src/modules/hevc_encoder.cpp`、`src/service/service_config.cpp`）：相机 1280×800@30 输出帧**中心裁切**为 1280×720（只裁不缩放）、按采集时刻选帧到 15 fps → BGRx → `nvvidconv` → `nvv4l2h264enc`（CBR、IDR 与 I 帧间隔 = GOP 30、B 帧 0、最低延迟硬件预设；插件没有字面叫 `zerolatency` 的属性）→ 帧标记 SEI → RTP 发本机 UDP → RTSP 服务线程按 TCP 转发（积压上限 500 ms）；地址 `rtsp://127.0.0.1:18084/rgb`（`pipeline.media.path`）。**不叠检测框**。同一帧零拷贝同时交给推流队列与推理队列，推流不等推理。H.265 只为复现早期诊断保留，🚫 作正式 MED-2。

> ③ **领导 2026-10-23 新需求（经用户）**：相机 MJPEG **原样**（原分辨率、原帧率、不叠框）直推上位机前端 HDMI 显示，H.264 保留为开关、不删。★ **同日领导（经用户）：MJPEG 路线暂缓，但仍要提速**（压显示延迟）。依据：实测相机 MJPEG 单帧约 106–108 KB（1280×800，办公室场景）⇒ 原样 30 fps 约 25 Mbit/s，约为现 H.264 2 Mbit/s 的 12 倍、网络模块无线实测约 9 Mbit/s（单位待确认）的 2.8 倍。⇒ **本期正式 MED-2 仍是上面①的 H.264**；低延迟改造（可选低延迟编码设置、预览帧率、视频快速通道等）在感知方开发分支，**未合入、未进正式版本**。
