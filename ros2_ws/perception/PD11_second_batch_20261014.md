# PD-11 第二批 · 预算重议材料第一批：采集时刻怎么取（未定项 C 的建议）、E 的正式值、上游时延实测、三个数的新读数（感知组，2026-10-14）

对应 `issues.md` 第 10 条答复与整机负责人裁定 U91：10.4(a) 要 E 的正式值；未定项 C 要感知的建议；10.4(b) 与 9.5-6 的预算重议要三个数（G-P2 60 / objects 200 / 语义 100）的读数和“上游相机内部处理”那一档的实测。请示与回执在 `issues.md` 第 11 条；本文是它的依据。

**一句话**：感知已按 `19` §2.4 的“首选”规则取采集时刻——相机的帧时间戳换算到主机单调钟，再减半个曝光，曝光逐帧取自相机元数据。这已在 1.8 上的开发版本里运行（10-14 起），固定链路估计 `latency_fallback_ms` 不再参与任何时间戳。实测误差全部在“偏旧”（保守）一侧：厂商约定成立时 1.1～3.5 ms；即使那条前提不成立，也只再偏旧至多约 17 ms。年龄读数因此比原来大 26～27 ms（三核）；两核时原来被常数掩盖的排队显出来了。三个门的数没有动。

## 一、未定项 C 的建议：用 §2.4 的首选规则，不用固定上界

### 1. 现在怎么取

```
相机： 曝光中点 ──半个曝光（逐帧，取自元数据）── 曝光结束 ＝ 帧时间戳（相机自己的钟）
主机： 每取到一个帧集，读一次“单调钟 / 原始单调钟 / 单调钟”（三连读，夹得不紧就重读）
       候选 G：SDK 把帧时间戳换算到主机钟的结果（SDK 后台定期向相机对时并拟合）
       候选 F：“取帧时刻 − 帧时间戳”的下包络（遇小即降、上升不超过 50 ppm）
               ＋ 标定的最短路径 30.767 ms（帧时间戳 → 取帧，最短的那一次）
       采集时刻 ＝ 可信候选中较旧的那个 − 2 ms 保护量；整毫秒向下取，必须递增
       G 可信：有值、随帧时间戳走（步长核对）、不在未来、不超过 5 秒
       F 可信：在同一次设备出流里与可信的 G 连续一致满 1 秒（锚定）
       两个都不可信 → 这一帧不给时刻，不往下游送，不发布
       每次设备出流的头 1 秒不给时刻（SDK 刚建对时，换算是短基线外推，见下）
       连续 5 秒有帧来、却一帧都打不上时刻 → 按采集故障退出，重启后重建对时
```

- 头 1 秒为什么不给：16 次启动实测，SDK 建设备时 150 ms 内连问 4 次时间，下一次问答在首帧后 0.23 秒。头 8 帧的换算是短基线外推，偏差 −5.1～+3.0 ms，16 次里有 4 次超过 2 ms 保护量、偏新。头 1 秒不给时刻后，25 份真实记录里没有一帧比参照新。
- 拔网线试验（10-14，链路断 8 秒，相机单独供电）：链路恢复后 SDK 把设备判为移除，原来那条流不再出帧，相机回到出厂地址。所以在产品里，“新的设备出流”只发生在服务启动时。

### 2. 为什么不用“固定上界”

- **固定量看不到排队。** 两核时帧在 SDK 队列里最多等 0.34 秒，固定量会把这些帧报成新鲜的（10.5 已报：年龄最多少报约 0.36 秒）。要用固定量盖住排队，上界得取到 400 ms 量级，平时每帧又报老约 350 ms。逐帧按相机时钟换算，排了多久就报多久。
- **曝光是自动的。** 今天的录制里，启动后头几秒深度曝光在 7.7～28.5 ms 之间变（116 帧），之后稳定在 30.108 ms。固定量要按最长曝光（30 fps 下 33.3 ms）取上界，平时每帧多报约 1.6 ms；逐帧取元数据就没有这一截。

### 3. 与整机侧“分两段”方向的对照

| 段 | 整机侧的方向（供参考） | 感知现在的做法 |
|---|---|---|
| 曝光那一段 | 逐帧用相机元数据 | 一致：每帧取“帧时间戳 − 传感器时间戳”（就是曝光的一半） |
| 传输＋相机内部处理那一段 | 固定上界写进配置 | 不用固定量，逐帧用相机时钟换算（看得到排队）。写进配置的是这一段的**最短值**（标定值），用来校准下包络 F |

### 4. “写进配置（可审计）”怎么满足

- 标定值 `capture_min_path_us: "30767"` 在配置文件里（`perception.pipeline` 的运行开关段，必填、不许 unset，随模型封存校验，启动日志打印）。
- 日志：启动时一行 `CAPTURE_CLOCK_CONFIG`；每 150 帧一行 `[CaptureClock]`（G / F 各打了多少、扣下多少、三个看门是否报警、最新时延）；扣下与恢复各一行。
- Status：只靠 F 打时刻时报 `t_capture_estimated`（固定值，含义正是“用主机侧估计兜底”）；有帧被扣下时报自由诊断串 `capture_time_unavailable`。两者都在最后一次发生后保持 1.5 秒。被扣下的那段不声明任何不计区间，照常计入 `infer_gap` / `infer_rate_low`。
- 契约里的 `perception.capture.latency_fallback_ms` 现在仍校验、仍打日志，但不参与任何时间戳。

### 5. 元数据曝光值的可靠性（整机侧要感知评估）

- 今天录的 5900 个深度帧里，“帧时间戳 − 传感器时间戳”与“曝光值 / 2”逐帧相等（±1 µs 取整），包括启动时曝光在变的那 116 帧。
- 这说明相机的三项元数据彼此自洽、随曝光逐帧变化。**它不是物理验证**：帧时间戳到底标的是不是曝光结束，仍是 10.4(a) 定为“按厂商约定、不做物理验证”的那条前提。
- 9 月以来所有录制的稳定段，曝光都是 30.108 ms（办公室灯光不变）。曝光大幅变化（关灯、室外强光）时的情形还没录到，下一批补。

### 6. 请定

- (a) 正式取法：采用 §2.4 首选规则（感知现做法）／改用固定上界／其他。
- (b) 标定值 `capture_min_path_us` 的位置：留在运行开关段（现状）／挪到 `perception.capture` 段（契约配置键）。
- (c) `perception.capture.latency_fallback_ms`：保留但不用（现状）／下次契约修订时撤掉或改义。

## 二、E 的正式值（10.4(a) 要的）

| 来源 | 大小 | 方向 | 依据 |
|---|---|---|---|
| 采集时刻相对参照（实测） | −2.65 ～ −1.11 ms | 偏旧 | 25 份回放（9 份服务录制、16 次启动）全部在 −2.51～−1.20 ms；10-14 在线核对 60 秒、3089 条消息在 −2.65～−1.11 ms |
| 参照本身的不确定 | ±0.8 ms | 两侧 | 参照＝帧时间戳经“对时问答拟合的直线”换到主机钟；问答完整往返中位 0.22 ms，残差在相机回值的毫秒取整之内 |
| 未经物理验证的前提（帧时间戳＝曝光结束） | 0 ～ 16.7 ms | 只会偏旧 | 若帧时间戳其实标的是曝光中点，采集时刻就多减了半个曝光；30 fps 下曝光最长 33.3 ms。曝光开始那种读法已排除（那样曝光后只剩约 1 ms 收齐整帧，传输都不够） |
| 两个候选前面共同的那段慢慢变长 | 看不出 | — | 已知局限：两个候选同时漂，任何看门都分不出；组件说明与用例里写明 |

**感知建议的 E**：
- 前提成立时：偏旧不超过 3.5 ms，偏新 0（−1.11 ms 加参照的 0.8 ms 仍在偏旧一侧）。
- 前提不成立时：偏旧不超过约 20 ms。
- **E 取 20 ms，全部在保守一侧**，远低于 PD-11 的 100 ms 重议门。

## 三、上游时延实测（重议要补的“相机内部处理”那一档）

在原始单调钟上量。帧时间戳经对时直线换到主机钟（不是实时可得的量，误差见上）。去掉每次启动后的头 300 帧。数为 p1 / 中位 / P99 / 最大，单位 ms：

| 录制 | 曝光中点 → 曝光结束（半个曝光） | 曝光结束 → SDK 收齐并组好这一帧 | SDK 组好 → 感知拿到帧集 | 曝光中点 → 拿到帧集 |
|---|---|---|---|---|
| 三核，30 分钟（10-14 凌晨，约 5.4 万帧） | 15.1 | 29.1 / 29.3 / 34.8 / 40.7 | 0.7 / 2.2 / 10.8 / 24.0 | 46.0 / 46.6 / 55.4 / 68.6 |
| 三核，5 分钟（10-14 凌晨） | 15.1 | 29.1 / 29.4 / 34.6 / 39.9 | 0.7 / 2.2 / 9.9 / 20.8 | 46.0 / 46.6 / 54.9 / 65.3 |
| 两核，5 分钟（10-14 凌晨） | 15.1 | 29.2 / 29.3 / 36.0 / 42.3 | 0.6 / 2.3 / 324.4 / 337.7 | 46.2 / 46.8 / 369.9 / 384.7 |
| 三核，接线后程序，60 秒（10-14 中午） | 15.1 | 29.1 / 29.2 / 34.2 / 38.0 | 0.7 / 2.1 / 11.3 / 16.1 | 46.0 / 46.5 / 55.6 / 60.4 |

与 `19` §2.2 前三行对照：

| §2.2 的档 | 预算 | 实测（三核中位） | 说明 |
|---|---|---|---|
| 曝光中点 → 帧完成 | ~17 ms | 15.1 ms | 就是半个曝光；随自动曝光变，30 fps 下最多 16.7 ms |
| GigE 传输 | ~4 ms | 合在 29.3 ms 里 | 640×400×16 bit 在千兆线上约 4.1 ms |
| （表里没有）相机内部处理、打包 | — | 约 25 ms | 29.3 − 4.1 推算，主机侧无法单独量；与整机侧 10.4(b) 的推算一致 |
| SDK 解包 → 槽 | ≤ 2 ms | 2.2 ms（P99 约 11 ms） | 含 SDK 帧同步与聚合、感知取帧线程排上核 |

- “相机内部处理约 25 ms”是推算值：主机只能看到“曝光结束 → SDK 收齐”整段，扣掉线路时间得出。相机内部怎么分（深度计算、打包、发送排队）看不到。
- 两核那一行的 P99 324 ms 不是相机变慢，而是感知取帧跟不上，帧在 SDK 队列里排队（10.5）。

接线后的程序自己跑的 60 秒在线核对（10-14 中午，三核，白天，每帧约 9.5 个目标）：Profile 82 / 128 / 144，Objects 161 / 199 / 219，与旧取法相比同样大 26～27 ms。

对三个数：
- **G-P2（Profile 发布时年龄 P99 ≤ 60 ms）**：新读数 95 ms（形态④）～132 ms（三核）。“PD-11 闭合前不签”不变；E 定了以后，这一门的读数就有了误差界。
- **objects 年龄一档 200 ms（控制拍上判）**：发布端 P99 185 ms（形态④）～207 ms（三核），最大 197～235 ms；到控制拍还要再加。
- **语义注入的陈旧上限 100 ms**：Objects 在发布时年龄中位就已超过 160 ms，Profile 检查时不可能新鲜。与旧读数（检查时仍新鲜的 0 帧）一致，只是离 100 ms 更远。
- **两核**：排队原来被常数掩盖，现在看得见了。Profile P99 396～453 ms、Objects P99 484～527 ms。整机侧 10.5 说的“两核不可取的又一条依据”依旧成立；理由从“年龄报错了”变成“年龄就是这么大”。

## 五、接线后整机侧能看到的变化

- `t_capture_mono_ms` 整体早 26～27 ms（三核），年龄读数相应变大；两核时变大得多（见上）。
- Status：`t_capture_estimated` 不再每条都带，只在只靠 F 打时刻时出现（在线核对 60 秒里 0 次）；新增自由串 `capture_time_unavailable`，服务启动后的头 1～3 条 Status 带它。
- 服务启动后的头 1 秒不发 Profile / Objects（首条 Objects 在首帧后约 1.4 秒）。
- 有帧来、却连续 5 秒打不上时刻：按采集故障退出，退出码 70，由服务单元重启。10-14 实测：用诊断库让 SDK 拿不到全局时间戳，服务在首帧后 5.03 秒（161 帧）报 `CAPTURE_TIME_LOST` 并以 70 退出。这期间没有发 Profile / Objects，Status 一直带 `capture_time_unavailable`，`fps_depth` 照常上升（被扣下的帧仍计入到达）。
- `fps_depth` 不受影响：被扣下的帧仍计入原始深度到达。整机侧 10.1 说过，`cam_rgbd` 只读 `fps_depth` 与心跳年龄。
- 以上都在 1.8 上我方隔离目录的开发版本里，还没有进正式交付包。
