# PD-11 首批材料：相机时间戳是什么、链路图、首批实测（感知组，2026-10-13）

对应 `issues.md` 第 9 条 9.4 答应先交的四样：身份、时间戳链路图、与 9 月旧探针的对账、实测办法与首批结果。结论与请示在 `issues.md` 10.4；本文是它的依据。

**一句话**：相机每帧带的时间戳是相机自己时钟上的时刻，不含传输。把它换算到主机时钟后，从深度曝光中点到感知拿到这一帧，1.8 空闲时约 **46 ms**；现在配置里的固定链路估计是 **23 ms**，偏小。上界值和误差界 E 还没有定。

## 二、SDK 给的几种时间戳各是什么

| SDK 接口 | 用的钟 | 表示的时刻 | 依据 |
|---|---|---|---|
| `getTimeStampUs()` | 相机自己的钟 | 按厂商约定是**曝光结束** | 元数据里的“传感器时间戳”恒等于它减去半个曝光时长（深度差 15.054 ms＝30.108 / 2） |
| 元数据 `SENSOR_TIMESTAMP` | 相机自己的钟 | **曝光中点** | 同上；即 `19` §2.4 首选规则要的那个量 |
| `getSystemTimeStampUs()` | 主机墙钟 | SDK 在主机上**收齐并组好这一帧**的时刻 | 比感知拿到帧集早约 1.8 ms |
| `getGlobalTimeStampUs()` | 主机墙钟 | SDK 把相机时刻**换算到主机钟**的结果 | SDK 后台定期向相机对时并拟合；换算关系每隔几秒会小跳一次（30 秒内 6 次，合计 2.8 ms） |

- 相机的钟不跟主机的钟：相对主机的原始单调钟快约 29 ppm。不能直接拿相机时间戳与主机钟相减。
- 深度与彩色的曝光结束时刻只差约 0.1 ms，曝光中点差约 10 ms（两路曝光时长不同）。
- 墙钟在这里只当测量工具用，不进入任何对外时间戳（`19` §2.4 的禁令没有变）。

## 三、时间戳链路图（感知现在怎么取）

```
相机： 深度曝光开始 ──30.1 ms── 曝光结束 ── 相机内部处理、打包 ── 以太网
                      ↑中点                ↑ 帧时间戳（相机钟）
主机： SDK 收包、组帧（系统时间戳，墙钟）
        → SDK 帧同步、聚合 → waitForFrameset 返回
        → 感知读一次主机单调钟：host_ready
        → t_capture ＝ host_ready − latency_fallback_ms（现为 23）
        → 取帧、几何、组包、put；t_publish 在 put 时取
```

- 感知现在只用 host_ready 和一个固定的减数；相机钟的时间戳只当帧的身份用。
- 23 这个值取自 `19` §2.2 表的前三行（17＋4＋2），是开发值，不是测出来的；Status 因此一直带 `t_capture_estimated`。

## 四、怎么量的，量到多少

**办法一（不依赖 SDK 换算好的全局时间戳，作为主结果）**
- SDK 有一个“问相机现在几点”的对时查询。打开 SDK 自己的调试日志可以读到每次问答的三个量：主机发出请求的时刻、完整来回的耗时、相机回的钟值。只在主机侧多写日志，不向相机写任何东西。
- 完整来回：中位 0.22 ms，范围 0.15–0.54 ms（56 次）。
- 相机一定是在“问出去”到“答回来”之间读的钟，所以每次问答都把“主机钟 − 相机钟”从两边夹住。全部样本合起来是一条直线，残差 ±0.5 ms（正好是相机回值的毫秒取整）；这条线能挪动的余地很小，由它算出的延迟最多偏 −0.6～＋0.1 ms。
- 把每帧的相机时间戳按这条线换到主机钟，再与 host_ready 相减。1.8 上只跑探针、不跑感知服务，3000 帧（去掉启动后前 10 秒再算，结果相同）：

| 起点 → 感知拿到帧集（host_ready） | 中位 | P99 | 最大 |
|---|---|---|---|
| 深度帧时间戳（按厂商约定是曝光结束） | 31.2 ms | 31.6 | 35.9 |
| 深度曝光中点 | 46.3 ms | 46.7 | 51.0 |

**办法二（用 SDK 的全局时间戳），并与 9 月旧探针对账**

| 量 | 9 月（另一台 Orin，150 帧） | 这次（1.8，900 帧） |
|---|---|---|
| 深度曝光结束 → SDK 组好这一帧 | 中位 28.7 ms | 中位 28.6，最大 30.7 ms |
| SDK 组好 → 感知拿到帧集 | 中位 1.7 ms | 中位 1.8，最大 3.8 ms |
| 深度曝光中点 → 感知拿到帧集 | 中位约 45.5 ms | 中位 45.4，P99 46.7，最大 48.0 ms |

两种办法相差约 1 ms；两台机器、相隔一个月的结果一致。

## 五、与 `19` §2.2 预算表前三行对照

| 预算行 | 预算 | 实测 |
|---|---|---|
| 曝光中点 → 帧完成 | 约 17 ms | 半个曝光时长 15 ms |
| GigE 传输＋SDK 解包 → 槽 | 4＋2＝6 ms | 曝光结束 → 感知拿到帧集约 31 ms |

多出来的约 25 ms 落在“曝光结束之后”。其中相机内部处理、网络、SDK 排队和组帧各占多少，这批数据拆不开，不作归因。

## 七、没有闭合的

1. “帧时间戳＝曝光结束”是厂商约定，元数据也按这个关系给曝光中点，但感知没有用物理手段独立验证。“时间戳在曝光开始”可以排除（那样曝光结束后只剩约 1 ms 就要收齐整帧，传输都不够）。所以真实值在 31～46 ms 之间，落在哪一头取决于这一条。
2. 对时查询问到的钟与帧时间戳用的钟是同一只——数据上吻合，没有独立证明。
3. 以上都是空闲状态。感知服务运行时主机更忙，分布还没有量。
4. 深度曝光是自动的，曝光中点那一项随场景变。

## 八、下一步

2. 第七节第 1 点是否用外部手段验证，等 `issues.md` 10.4 (a) 的答复。
3. 据以上两项定上界值和 E；定之前配置不动，年龄继续按估计值报、不签。
