## 一、一句话

- **put（发送）**：三核下 Profile 每 100 次约 2 次超过 1 ms；超时的八成多是线程排队等核，一成多是“睡着等”——几乎每次都与另一路（Objects）的慢发送重叠，推断是两路共用一个会话里的锁、持锁线程被挤下核。没有分片、没有发了没收到。**形态④ 下 put P99 0.66～0.75 ms，达到 1 ms；三核下 1.9～3.8 ms，达不到。**
- **服务里比离线慢**：主因是环境，不是活变多。同一批冻结帧、同一个程序，只要服务在跑，几何段的线程 CPU 就涨 26～31%，与服务里看到的 +27% 对得上；涨在每帧扫整幅图的几遍循环（每像素访存变贵），地面拟合基本不涨。剖面快线在服务里的 CPU 成本应按离线 × 约 1.3 估。
- **外参通用分支**：外参带水平偏移时，扫描从 4.6 变成 7.8 ms，整条快线 +3.7 ms；拟合与分支无关。新预算应按通用分支定。
- **地面拟合**：每帧在约 5.5 万个候选点上反复读最多约 73 遍，均值 7.2 ms，是剖面快线里最贵的一段；§2.2 的预算表没有这一项。

## 二、put 的 P99 超 1 ms：有没有阻塞

### 2.1 量的是什么
- 服务日志里的 put 只量“把这一包交给 zenoh”那一次调用（`z_publisher_put`），分配、拷贝、记账都不在里面；我方代码在这一段里不加锁、不等待。
- zenoh 的拥塞设置是默认值（同一个库读回）：丢弃模式下发送队列满时先等最多 1 ms 再丢；要分片的大消息（超过约 64 KB 一批）最多等 50 ms；每个优先级 2 批、发送线程 2 个。

### 2.2 怎么量的（pp1014b，1.8 时钟 10-14 17:56–18:06；E:putprobe_20261014/）
- 诊断版程序：在发送调用前后读本线程的 CPU 时间、排队等核时间（schedstat）和主动 / 被动切换次数，超过 1 ms 的每一次记一行。zenoh 是静态链接进程序的，所以探针写在源码里，单独编了一个诊断版；交付代码没动。
- 三窗：诊断版、产品版、诊断版，各 180 秒，三核（2、3、7），同一场景。分类规则开测前写定（D:预登记 10-14）：
  - **等核**：没有主动切换、有被动切换，排队时间 ≥ 0.7 ×（墙钟 − CPU）；
  - **阻塞**：有主动切换，且睡眠（墙钟 − CPU − 排队）≥ 0.3 ms；
  - **自己忙**：CPU ≥ 0.5 ms。

### 2.3 结果

| | Profile（两窗） | Objects（两窗） |
|---|---|---|
| 发送次数 | 4919 / 4912 | 4508 / 4514 |
| 超过 1 ms 的占比 | 2.07% / 2.02% | 5.88% / 5.47% |
| 其中：等核 / 阻塞 / 自己忙 / 其他 | 84 / 16 / 0 / 5；88 / 13 / 0 / 0 | 263 / 6 / 0 / 7；253 / 4 / 0 / 1 |
| 最长一次 | 14.7 / 15.4 ms | 17.3 / 15.0 ms |
| 最长睡眠 | 8.6 / 6.0 ms | 9.3 / 5.1 ms |
| 包最大 | 13.2 KB（不分片） | 11.9 KB（不分片） |

- 三窗服务记的 Profile 发送条数与抓包收到的条数**逐条相等**（5192 / 5191 / 5193）：没有“发了没收到”，即“等满 1 ms 后丢弃”一次也没发生。
- “阻塞”共 39 次：每次恰好一次主动切换，睡 0.3～9.3 ms（不集中在 1 ms，不像“等满再丢”），**除 1 次外都与另一路的慢发送在时间上重叠**。不阻塞的那些，排队时间 ≈ 墙钟 − CPU（中位比 1.01）。
- **推断（未证实）**：Profile 与 Objects 共用一个 RT 会话，发送时拿会话里的同一把锁；持锁线程被挤下核时，另一线程睡着等。根子仍是等核。zenoh 源码不在设备上，锁这一层没有直接读数；感知不打算为此做“两路各用一个会话”的对照（④ 下已达标）。
- 局限：开探针的窗里服务自报 put P99 3.2 ms、不开 1.9 ms；但同配置没有探针的三窗本身就在 2.3～3.8 ms 之间，探针本身的影响分辨不出。

### 2.4 与摆法的关系
| 形态 | 服务自报 put P99 | 出处 |
|---|---|---|
| 三核 | 2.99 ms（30 分钟窗）；1.9～3.8 ms（180 秒窗） | wm1014N_A1；pp1014 / pp1014b |
| 形态④ | 0.75 / 0.66 ms（30 分钟窗） | wm1014N_D1 / D2 |

## 三、服务里为什么比离线慢（同输入对照 si1014 / si1014b，1.8 时钟 10-14 19:10–19:28；E:sameinput_20261014/）

### 3.1 怎么量的
- 同一个冻结的几何压测程序、同一组冻结帧（10-13 当前场景录的 150 帧）、每次回放 4 遍、单回放线程；**只换环境**。产品代码不动。判读规则开测前写定（D:预登记 10-14）。
- 每种环境两遍、前后对称排序；18 遍的输出摘要全部相同（同输入同输出）。

### 3.2 结果（几何＋网格整段的线程 CPU 中位，两遍均值）

| 环境 | 线程 CPU | 对无服务基线 | 主要涨在 |
|---|---|---|---|
| 无服务，压测在核 2 / 核 3 / 核 7 | 16.90 / 16.90 / 16.85 ms | —（三颗核没有差别） | — |
| 服务在核 2、3（簇 0），压测在核 7（簇 1，独占） | 21.35 ms | **+26%** | 扫描 +42%、分类 +35%、高度窗 +61%、网格 +23%；拟合 +12%（两遍不稳） |
| 服务照常在核 2、3、7，压测也在核 2 | 22.10 ms | **+31%** | 各段都涨；墙钟中位 36 ms（压测被挤下核） |
| 无服务，核 3 跑一个 64 MB 反复拷贝（同簇） | 22.75 ms | +35% | 扫描 +75%、分类 +71%、高度窗 +80%、网格 +19%；**拟合 +0.5%** |
| 无服务，核 7 跑同样的拷贝（另一簇） | 17.35 ms | +2.7% | 各段 +2～8% |

- 1.8 的缓存：每核 L2 256 KB，核 0～3 共用 L3 2 MB（另一簇同样）。像素记录数组 12.3 MB，远大于 L3。

### 3.3 读法
- **主因是环境**：压测独占一核、服务在另一簇（第二行）也涨 26%，所以不是抢占；同一批帧同一个程序，所以不是输入或程序不同。涨幅与服务里观察到的 +27%（整步线程 CPU 21.5 对离线 16.9）对得上。
- **涨的是“每像素访存”**：扫描、分类、高度窗、网格证据这几遍每帧都要流式读写十几 MB，最敏感；拟合在约 1.3 MB 的候选数组上反复读（放得进 L3），基本不受影响。
- **CPU 侧的拷贝只拖同一簇**（同簇 +35%、跨簇 +3%），而**服务跨簇也拖 26%**。推断：服务的影响不只来自 CPU 线程，还经过整机内存——推理（DLA）、视频编码、JPEG 解码等加速器与 CPU 共用内存控制器。**未证实**：非 root 读不到内存控制器占用。
- 对预算的含义：剖面快线在服务里的 CPU 成本按离线 × 约 1.3 估；第四节通用分支的 +3.7 ms 是离线数，在服务里也会被同样放大。
- 感知自己的减活方向（不在本批）：48 B 的像素记录每帧写一次、读两次——瘦身记录或合并遍数，能直接降低对内存争用的敏感度。
- 局限：都是指示值；服务那几窗是诊断窗，场景与长窗相同（每帧约 11 个目标）；“服务只占同一簇另外两颗核”的组合做不出来（采集线程要求服务的核里同时有 2 和 3，而核 0、1 不在我们可用范围），用“服务在另一簇”代替。

## 四、外参通用分支（geooffset1013；E:pstage_20261013/geobench1013.extract.txt；D:4842）

| 段 | 平移 [0, 0, 0.547]（快速分支） | 平移 [0.30, 0, 0.547]（通用分支） | 差 | 原因（代码） |
|---|---|---|---|---|
| 扫描 | 4.59 ms | 7.83 ms | +3.24 | 每个有效像素多一次斜边与扇区查找（几次除法、叉积）；同时少读 5.1 MB 预算表——多出来的是算术，不是访存 |
| 拟合 | 6.53 | 6.52 | 0 | 与分支无关 |
| 分类＋高度窗 | 2.70 | 3.00 | +0.30 | 高度由一次乘加变成算点＋点积 |
| 网格 | 2.76 | 2.86 | +0.10 | |
| 合计（中位） | 16.5 | 20.2 | **+3.7** | |

- 所有上机配置的外参都是占位值（相机相对机体原点没有水平偏移），服务和离线现在都走快速分支。0.30 m 是假设值，真实值要等外壳与标定。
- 同一冻结帧集（day1004）、单回放线程、核 2。scene1013 没有跑过通用分支，按差值推约 16.9 ＋ 3.7 ≈ 20.6 ms（推算）。

## 五、地面拟合与三遍整幅循环的工作量账（离线 geoscene1013：scene1013 冻结帧 150 帧 × 4 遍，单回放线程、核 2）

| 段 | 每帧迭代什么 | 每帧数量 | 实测（均值） | 每元素 |
|---|---|---|---|---|
| 扫描 | 全部原生像素；每个重写一条 48 B 像素记录，有效深度像素再算点、距离、扇区，近处贴地的点收进拟合候选 | 256 000 像素 | 4.20 ms | 16.4 ns / 像素 |
| 拟合：先验平面打分 | 候选点 2 遍 | 约 5.5 万点 × 2 | 0.40 ms | 3.6 ns / 点·遍 |
| 拟合：假设筛选 | 63 个随机三点平面 × 候选点，每 4096 点可提前放弃；够格的再完整打分（每帧约 4 次） | ≤ 约 368 万次（上限） | 3.51 ms | 取决于提前放弃，只有上下限 |
| 拟合：三轮精修 | 4 遍全部候选，逐点累加（串行依赖） | 约 22 万 | 3.32 ms | 15.1 ns / 点·遍 |
| 分类 | 全部像素；感兴趣区内有效像素各一次除法 | 256 000（区内 135 397） | 2.32 ms | 9.1 ns / 像素 |
| 高度窗 | 本帧“障碍”类像素 | 随场景变 | 0.54 ms | — |
| 网格证据 | 全部 256 000 条像素记录 | 256 000 | 2.35 ms | 9.2 ns / 像素 |
| 网格其余（清零、期望票、逐扇区） | 181 扇区 × 不超过 24 格 | 约 4 300 格 | 0.28 ms | — |
| **合计** | | | **16.9 ms**（线程 CPU 中位 16.9） | |

- **为什么是三遍整幅循环**：分类要等拟合出的平面；网格的盲区要等全部像素分完类才知道最近地面。设计表按“整幅单遍、每像素约 30 次运算”估，实际是三遍，再加拟合在约 1.3 MB 候选数组上最多约 73 遍反复读。
- **拟合 7.2 ms 是单段最大**，`19` §2.2 的预算表没有这一项（整机侧 9.3 已认定为“预算表漏了地面拟合”）。
- 随画面变的：有效像素数、候选点数（0.6～3 m 内贴地的点）、画面平不平（决定提前放弃多少）、障碍像素数。空旷大地面时候选点能到多少还没量过。
- 1.8 的缓存（10-14 读 sysfs）：每核 L1 数据 64 KB、L2 256 KB，核 0～3 共用 L3 2 MB。像素记录数组 12.3 MB 远大于 L3（三遍整幅循环每帧都要走内存）；拟合候选约 1.3 MB 放得进 L3。
